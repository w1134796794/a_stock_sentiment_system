# 当前系统完整逻辑与高星量化项目对照

> 核对时间：2026-09-26。依据当前本地工作树与 GitHub 官方仓库。本文描述“代码如何设计”，不代表服务器部署、定时任务或实时行情已实测正常。工作树已有未提交修改，线上行为还取决于部署版本、环境变量和当日数据。

## 一张图看全链路

```text
交易日盘后自动任务（默认 20:00，Asia/Shanghai）
  -> 取数与质量检查 -> Silver/DuckDB -> 市场/龙虎榜/短线信号/板块/个股因子
  -> 五套生产策略独立筛选 -> 合并去重、市场与拥挤门控 -> 决策池/页面快照
次日 09:25 竞价预警 -> 盘中批量行情、分钟线、板块成分股强度
  -> 昨日候选分时确认 + 独立龙头池盘中转强观察
  -> 微信买点提醒 / 模拟买入、换仓 -> 持仓风险与卖点提醒 / 模拟卖出
  -> 历史成交、复盘、回测与工作台展示
```

### 1. 数据和自动化

| 阶段 | 当前实现 | 主要入口与产物 |
| --- | --- | --- |
| 自动触发 | 内置调度器按上海时区检查交易日；竞价默认 09:25:10，盘后默认 20:00。每日任务有租约、状态、失败重试和隔离子进程。 | `core/automation/internal_scheduler.py`、`scripts/automation_daily_worker.py`；任务状态和日志 |
| 盘后取数 | `DataPrep` 组织日线、板块等源数据；检查收盘时点及数据完整性，必要时强制重取。数据不齐时不应继续生成“成功”的候选。 | `core/etl/daily_pipeline.py`；Silver 数据、质量状态 |
| 因子计算 | 按市场、龙虎榜、短线信号、板块、个股的顺序运行，结果写入 DuckDB 因子仓库。 | `core/factors/jobs/runner.py`、各 `*_factor_job.py` |
| 页面读模型 | 策略结果、决策池、分析摘要和快照落到 `webdata`；工作台按日期读取并短期缓存。 | `core/etl/daily_pipeline.py`、`core/application/workbench_service.py`、`snapshot/writer.py` |

这里的 Silver/DuckDB、JSON/SQLite 快照、Redis 实时缓存承担不同职责。它们不是三套独立策略数据源：盘后用可复现的日期分区，盘中用带时间戳和有效期的实时数据，页面尽量读已生成的结果。**实际运行是否完整**应核验当天 Silver 质量报告、五个因子任务状态、决策池文件和调度器状态；仅凭页面为空不能判定是哪一层失败。

### 2. 因子到底在算什么

- **市场**：涨跌停、涨跌家数、成交量、连板晋级、指数与情绪阶段，形成市场分和赚钱效应等背景判断。赚钱效应分及其短期变化见 `core/factors/jobs/market_factor_job.py`；情绪阶段见 `core/analysis/emotion_phase_model.py`。
- **板块/主线**：板块强度、相对强弱、共振、拥挤或衰退，用于判断个股的上涨是否有同题材支持；盘中板块强度由同花顺成分语义和成分股批量行情辅助验证，见 `core/realtime/sector_breadth.py`。
- **个股结构**：流动性、相对板块强度、封板质量、注意形成、弱转强修复、龙头身份，以及近期涨停回踩/跌停反包的前置结构，见 `core/factors/jobs/stock_factor_job.py` 和相关短线因子任务。
- **辅助证据**：龙虎榜席位与拥挤、量价健康、资金认可等可用于排序、否决或解释，并非单个高分就自动买入。

盘后因子回答“明天值得观察谁”，盘中分钟与盘口证据回答“此刻是否触发”。前者不应直接当成交价或买点。

### 3. 选股与龙头是两层

当前 `config/strategy_combinations.yaml` 启用五套生产策略，策略配置可经 `core/screening/strategy_profiles.py` 持久化覆盖；不能只看 YAML 默认值判断线上阈值。

| 生产策略 | 盘后要找的结构 | 次日定位 |
| --- | --- | --- |
| 主线龙头候选 `mainline_leader` | 主线地位、板块共振、相对板块不弱，加连板/明确龙头标签或中期趋势领先身份；衰退或龙虎榜过度拥挤可否决。 | 主线候选，仍待分时确认；市场风险影响是否参与/仓位，不应抹掉龙头身份。 |
| 弱转强修复 `weak_to_strong` | 修复信号、板块同步、流动性和最低市场环境；此外代码要求历史龙头池身份。 | 次日按弱转强分时条件确认，不因盘后“修复”就买。 |
| 首板启动 `first_board_launch` | 官方首板身份、涨停确认、注意形成、基础流动性、封板质量及市场扩散基础。 | 首板候选，避免用涨幅阈值冒充真实首板。 |
| 涨停回踩 `limit_pullback` | 近期涨停后回到预定支撑附近且未有效破位，具备流动性与缩量/相对强度。 | 等盘中承接、量价突破等结构确认。 |
| 跌停反包 `limit_reversal` | 近期跌停事件后的修复结构，排除连续跌停或破位，兼看流动性和恢复程度。 | 等盘中站稳反包目标并确认突破。 |

`ScreeningEngine` 对各策略分别筛选和排序；`DecisionPoolService` 再合并同票命中、市场情绪/可执行性、同题材拥挤及行动分组，输出“重点确认 / 盘中观察 / 暂不参与”和排除理由。**龙头池不是这五套策略的简单重命名**：`LeaderPoolService` 从独立的市场身份和历史事件识别核心、板块、情绪、趋势等角色，候选名次只供观察排序；盘中转强有独立观察入口。因此“昨日候选”和“当日龙头”可能不重合。

### 4. 盘中确认、通知和交易

1. `eltdx` 采集器按监控名单批量取报价（默认约 3 秒轮询），共享部署要求 Redis；分钟线另行同步，避免慢分钟请求阻断报价轮询。`RealtimeQuoteService` 通过 `DataManager` 取批量快照并标记陈旧；数据源详情和兜底以实际环境配置为准，见 `core/realtime/eltdx_collector.py`、`core/realtime/quote_service.py`。
2. `EntrySignalService` 将候选、当天报价、分钟线、竞价和板块同步证据组合。报价日期不符或已过期会保持观察；分时确认与回测共用 `backtest/minute_entry.py` 的核心规则，结构策略各有专用入场模式。分钟信号只能在确认分钟结束后使用，不能用同一分钟较低价回填成交，见 `core/realtime/entry_signal_service.py`。
3. `RealtimeOverlayService` 读取昨日决策池并叠加今日确认结果；龙头池盘中转强另有观察路径。`NotificationService` 对实时信号做去重、同题材数量约束并支持多 Server 酱接收方，也提供卖点提醒，见 `core/realtime/overlay_service.py`、`core/notifications/notifier.py`。
4. 模拟交易初始资产默认 100 万、最多 3 只、基础单仓 34%；确认后可买，现金不足时比较新候选与可卖持仓强度，达到换仓优势阈值才轮换，受 T+1 约束。可手动录入持仓；历史回放和回测可导入模拟账本。它是**模拟成交**，不是券商实盘委托，见 `config/settings.py`、`core/portfolio/paper_trading_service.py`、`core/portfolio/holding_service.py`。
5. 持仓监控把个股结构/保护价、市场与板块环境及配置化退出规则一起判断；保存退出信号，微信通知失败可重试，符合条件时处理模拟卖出。过期或缺失行情不应被当作可执行卖价，见 `core/portfolio/exit_decision_service.py`、`core/portfolio/position_monitor.py`。历史成交和账户展示来自持仓仓库。

### 5. 研究/运行边界

- 回测有分钟成交、滑点、费用、T+1 等规则，但实时报价、历史分钟、竞价及板块观察的可得时间仍要逐字段核对；“共用规则”不等于历史回放和实盘完全等价。
- 赚钱效应、晋级梯队与其趋势是市场环境读数，不是独立买入指令。策略参数改动应记录配置版本，并用时序样本验证；不能用同一批样本反复调阈值后再把该样本当作验证集。
- 源数据覆盖、交易日完整性、同花顺行业/概念代码映射、实时报价延迟和 Redis 健康度，都是生产正确性的前提。缺数据时明确显示“证据不足/继续观察”比推断可交易更可靠。

星标约数为 **2026-09-26 查询时** 的仓库页面/API 快照，只用于筛选成熟项目，不能证明策略收益。以下均参考项目官方仓库或其官方文档。

| 项目 | 约星标 | 真正值得借鉴 | 对本项目的适配判断 |
| --- | ---: | --- | --- |
| [Microsoft Qlib](https://github.com/microsoft/qlib) | 4.89 万 | [Point-in-Time 数据](https://github.com/microsoft/qlib/blob/main/docs/advanced/PIT.rst)避免历史数据修订泄漏；[Recorder](https://github.com/microsoft/qlib/blob/main/docs/component/recorder.rst)管理实验、指标和回测产物。 | **高**：给因子、策略、数据快照做版本化和可重放；不必为了此事整体引入其 AI 训练栈。 |
| [vn.py](https://github.com/vnpy/vnpy) | 4.56 万 | [事件引擎/网关](https://github.com/vnpy/vnpy/blob/master/vnpy/trader/engine.py)把行情、委托、成交、持仓、账户作为不同事件和对象；[网关接口](https://github.com/vnpy/vnpy/blob/master/vnpy/trader/gateway.py)约束重连与线程安全。 | **高**：统一“信号-提醒-模拟委托-成交-持仓”事件语义与幂等键；现阶段无需接券商网关。 |
| [QuantConnect LEAN](https://github.com/QuantConnect/Lean) | 2.18 万 | 事件驱动、可替换模块、回测与实时共用算法框架；重视成交/账户建模。 | **中高**：做真实可成交性、盘口缺失、涨跌停、停牌及部分成交的场景测试；完整引擎迁移成本过高。 |
| [RQAlpha](https://github.com/ricequant/rqalpha) | 0.68 万 | 面向 A 股的可替换 Mod 架构和回测/模拟交易，强调交易日、合约、停牌等市场基础数据。 | **中高**：核对本项目 T+1、100 股整手、停牌/复权/除权、手续费和印花税；谨慎区分开源框架与其商业数据服务。 |

上述“适配判断”是基于这些项目的设计与本项目代码现状所作的工程推断，不是上游项目对本系统的认证。星标量和盈利能力无因果关系。

## 建议落地顺序

| 优先级 | 建议 | 最小可验收结果 |
| --- | --- | --- |
| P0 | 建一份“信号时点证据包”：候选日/行情日、源数据时间、报价接收时间、分钟收盘时间、板块观测时间、配置版本、触发/否决原因、模拟成交时间。借鉴 Qlib PIT 与 vn.py 事件对象。 | 任意一条微信买卖提醒，都能按证据包复盘为何发/没发，历史回放不读未来数据。 |
| P0 | 做盘后及盘中双健康门禁：Silver 分区完整、因子任务逐项成功、决策池与快照同日期；盘中检测 Redis/采集器租约、行情年龄、板块覆盖率。 | 缺数据时不产出“成功买点”；工作台直接指出哪一层缺失及上次成功时间。 |
| P1 | 建“信号-模拟委托-模拟成交-持仓变化-通知”统一流水，给每条事件稳定 ID 与幂等键。 | 重试、刷新、服务重启均不重复买卖或重复推送，同一事件能追到持仓和成交记录。 |
| P1 | 建策略实验台账：参数/因子/数据版本固定，按时间滚动样本外检验五策略和市场阶段，记录候选数、盘中确认率、可成交率、收益与回撤。 | 可以回答某策略阈值改动是在改善样本外表现，还是仅把历史拟合得更漂亮。 |
| P2 | 加强 A 股成交模型与压力场景：涨跌停封单、停牌、极低流动性、竞价到分钟切换、卖出 T+1 限制、交易成本。 | 相同日期与信号下，回放成交不早于可知信号时间；不可成交时留下明确拒绝记录。 |

**不建议现在做**：为了星标高而重写成 Qlib/LEAN、无验证地增加机器学习选股、同时维护多套行情语义。先把现有同花顺板块语义、`eltdx` 行情时点、五策略决策池和模拟账本贯通、留痕、可验证，收益更大。
