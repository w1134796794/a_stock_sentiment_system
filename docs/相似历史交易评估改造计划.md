# 相似历史交易评估改造计划

编制日期：2026-10-07。更新：2026-10-08。Phase 0—4 已完成基础实现；Phase 5—6 仍为实施计划。
部署、历史补建、数据覆盖和当前边界见《信号案例库使用说明.md》。
匹配、滚动验证与旁路记录见《相似评估与滚动验证使用说明.md》。账户过滤/换股对照尚未实现，不能用独立信号收益代替。

## 1. 目标与实施边界

在盘中规则确认之后，对当前信号寻找历史相似案例，回答四个问题：

1. 按指定退出规则交易，扣除成本后盈利的概率是多少？
2. 盈利时通常赚多少，亏损时通常亏多少？
3. 买入后可能经历怎样的波动、收益范围和下行情景？
4. 相比其他新信号及现有持仓，该信号对账户是否更有价值？

实现顺序为：可追溯的案例与结果 → 相似统计 → 独立验证 → 展示与通知 → 账户决策试验。

初版只增加参考评估，不改变现有策略入场条件、仓位上限、退出规则或微信信号触发条件。没有足够证据时显示“样本不足”，不以50%填充缺失概率。后续自动买卖接入必须由固定版本的样本外与账户实验支持。

## 2. 已有功能与主要缺口

| 现有位置 | 可复用内容 | 需要补齐的问题 |
|---|---|---|
| `core/operations/evidence.py` | 信号ID、候选日、行情日、报价和板块观测时间、配置版本 | 补齐信号时点市场、身份、日线与分时特征；保留首次触发事实 |
| `core/operations/ledger.py` | 信号证据、交易事件、实验与净值表 | 增加案例、成熟结果、不可变预测及匹配明细 |
| `backtest/backtest_engine.py` | 盘中确认、入场尝试、成交、退出、账户回放 | 输出不受账户资金和持仓数量筛掉的可成交信号案例 |
| `core/signals/confidence_service.py` | 历史信号统计、概率展示、可靠度与置信等级 | 现有统计按入场模式汇总；只过滤入场日期，未严格过滤结果结束时间 |
| `core/realtime/entry_signal_service.py` | 分时结构及确认结果 | 在确认时冻结特征，引用相似评估结果 |
| `core/operations/experiments.py`、`equity.py` | 实验记录、时间窗口和账户净值评估 | 增加预测校准、相似模型对照、尾部风险及换股实验 |

现有“成功概率”不能直接重命名为“相似个股盈利概率”。旧统计和新评估要有明确的来源与标签。

## 3. 统一定义

### 3.1 主评估口径

主成功事件：在指定入场及退出版本下，完整平仓后的净收益大于零。

净收益包含佣金、卖出税费和明确的成交估计成本。滑点已体现在成交价时不再重复扣除。部分卖出与加减仓应按完整交易段累计现金流，不把一次减仓当成整笔成功。

同时输出：

- 净盈利概率及其统计区间。
- 平均净收益、中位净收益、平均盈利、平均亏损绝对值、盈亏比。
- 盈利因子：盈利交易总收益／亏损交易总损失绝对值，与盈亏比分开展示。
- 未来第1、3、5个交易日收盘相对可成交入场价的收益分布。
- 成交后最大浮盈MFE、最大浮亏MAE，以及在指定观测区间内的下行尾部。
- 可成交率、无法成交原因、缺失证据比例。

盈亏比需要同时存在盈利和亏损样本；没有亏损时返回“不足以估计”，不显示无限优势。未来收益分位范围与盈利概率的统计置信区间是两种不同概念，界面分开展示。

### 3.2 三种样本必须区分

| 样本 | 用途 | 限制 |
|---|---|---|
| 全部候选与确认尝试 | 检查确认率、数据缺失和不可成交原因 | 不能直接作为已成交交易胜率的分母 |
| 可成交信号的独立标准化交易 | 学习信号本身的后续表现 | 不受真实账户资金、3只持仓上限筛选；采用统一且合法的交易单位与退出规则 |
| 实际模拟账户交易 | 检查资金、持仓、换股及真实账户净值 | 受账户选择影响，不替代完整信号案例库 |

手工成交继续保留在账户中，来源标为manual。没有策略确认特征的手工成交不自动混入策略相似样本库。

## 4. Phase 0：修正历史概率的时间与版本口径

修改：`core/signals/confidence_service.py`、`core/realtime/entry_signal_service.py`、相关历史统计测试。

具体工作：

1. 历史交易必须在预测时点之前完整结束；只满足买入日期在前不够。
2. 结果对应的退出时间、结果可获得时间和来源批次必须可追溯。缺少时点的旧样本仅进入探索统计。
3. 按策略、入场模式、退出规则、成本假设及兼容版本分组。不能把不同参数重复回测的结果拼成更多独立样本。
4. 建立同股票、交易日、确认模式的重复事件归并规则；多个策略共识保留为特征和归因信息，不重复算成多笔交易。
5. 已有历史汇总率显示为“入场模式历史统计”；样本不足和未校准状态明确暴露给API。

验收：预测时间之后的平仓结果不能进入统计；同一事件多次回放不增加样本数；不同退出版本不会无提示合并；无样本不输出伪概率。

## 5. Phase 1：建立信号时点案例库

新增：`core/signals/case_repository.py`、`core/signals/case_features.py`。

扩展：`core/operations/evidence.py`、`core/operations/ledger.py`、实时信号和历史回放输出。

每个案例记录以下字段：

| 类别 | 主要字段 |
|---|---|
| 身份与版本 | case_id、signal_id、股票、策略来源、确认模式、配置/特征/数据版本、实时或重建来源 |
| 时间 | candidate_date、market_date、confirm_at、feature_cutoff_at、observed_at、received_at、recorded_at |
| 市场 | 市场分、情绪阶段、赚钱效应、指数涨跌、晋级趋势、题材拥挤度 |
| 股票身份 | 龙头角色、生命周期、连续身份天数、连板高度、10/20cm类别、流动性与规模 |
| 日线 | 近期收益、回撤、距阶段高点与支撑的距离、成交额倍率、主线与资金因子 |
| 分时 | 开盘幅度、确认时段、距VWAP/开盘区间距离、成交进度、假突破、承接和板块宽度 |
| 质量 | 缺失字段、有效覆盖、VWAP来源、成交证据精度、板块观测年龄 |

字段标准化优先使用已有因子与分钟结构结果。缺失值保留缺失标记，不能用中性50分或0代替真实观测。

冻结首次有效确认特征，后续报价刷新不覆盖它。后续观察可保留独立事件。使用全部当日分钟数据计算的特征，必须切断到确认时点，不能包含确认之后的最高价、全天成交量等。

历史重建记录市场事件时间和实际重建时间。只有能够证明当时可获得的特征才进入严格验证；使用后来修订数据的案例标记为重建研究，不能称为当时真实预测。

验收：输入数据增加确认后的分钟，冻结特征不变化；缺失字段可审计；重复运行幂等；五策略和龙头观察来源都有案例记录。

## 6. Phase 2：计算成熟结果与独立信号交易

新增：`core/signals/case_outcomes.py`、`scripts/build_signal_cases.py`。

复用现有分钟入场、退出引擎及交易日历，扩展历史回放的案例输出。策略为主线龙头、弱转强、首板启动、涨停回踩和跌停反包；龙头观察的入场来源单独保留。

具体工作：

1. 先记录确认，再判定是否存在可成交证据，最后模拟独立标准化交易。
2. 入场价使用确认后的合法成交估计；单纯触及涨停不视为一定成交。
3. 根据T+1、停牌、涨跌停、分钟精度和成本版本生成退出结果。跌破保护价不保证按保护价卖出。
4. 为净收益、D+1/3/5、MFE/MAE各记录label_end_at和available_at；不同结果按各自成熟时间解锁。
5. 浮盈浮亏只从成交后开始计算；分钟内先后顺序不确定时标记模糊证据并采用已规定的保守口径。
6. 部分卖出累计费用与现金流；仍持仓的交易标pending，不算失败或成功。
7. 缺分钟、缺板块和缺日线标blocked/missing，不转换成“没有机会”。

盘后任务只补新增或刚成熟结果。某个案例缺证据可以阻断该案例，其他案例继续计算；与必须连续提交的账户接力回放区别处理。

验收：未来结果在成熟前不可查询为已知结果；每个独立交易能追溯到确认与成交；成本对账正确；缺数据、未成交、未平仓和亏损四种情况分别记录。

## 7. Phase 3：相似匹配与统计评估

新增：`core/signals/similar_case_service.py`，复用现有可靠度与统计区间工具。

匹配流程：

1. 只读取在预测时点已成熟、数据质量合格且版本兼容的案例。
2. 先按策略/确认模式、涨跌幅类别和成交证据口径建立可比集合。
3. 优先匹配相同情绪阶段、龙头身份和确认时段，再比较日线位置、成交进度、板块强度等连续特征。
4. 连续特征使用训练窗口内的尺度标准化；按业务类别加权，避免几十个相近因子重复支配距离。
5. 返回相似度最高的案例和不相似的主要原因；相似度低时拒绝给出个股级估计。
6. 按距离与时间衰减进行加权统计，向同策略、同环境基准收缩，降低小样本极端胜率影响。
7. 输出raw_sample_count、权重有效样本数、交易日数、主题覆盖和回退层级。权重有效样本数不等于独立样本数。

初始邻居数、相似度门槛和特征权重作为研究配置；在Phase 4的训练窗口中选择并冻结，不能根据测试期收益随意调整。

回退层级：精细相似案例 → 同策略/模式/市场阶段 → 同策略/模式 → 无可靠概率。每层仍遵守版本与时间边界，并显示所用口径。

概率区间与收益稳定性按交易日分块评估，并检查同日同主题集中度。不能把同一天同题材的几十个信号当成几十次独立试验。

输出包括概率、预期净收益、盈亏比、尾部收益范围、基准提升、样本可靠度和案例列表。成功与失败案例均可展示，不只选择好看的历史走势。

验收：同样输入与版本输出一致；未来案例不可入选；不同绝对股价不支配距离；小样本回退有解释；没有亏损样本不会输出无限盈亏比。

## 8. Phase 4：滚动样本外验证与概率校准

新增：`core/signals/similarity_validation.py`。

扩展：`core/operations/experiments.py`、`scripts/strategy_experiment_ledger.py`、策略评估报告。

验证流程：按交易日依次划分训练、校准、测试窗口。训练决定匹配规则，独立校准窗口调整概率，测试窗口只评估一次。标签观测期重叠的训练案例需剔除或隔离。

验证必须记录三组对照：现有规则、按模式/环境分组的简单历史基准、相似案例评估。新功能需证明比简单基准提供了额外信息。

| 检查项 | 评估内容 |
|---|---|
| 概率准确性 | Brier分数、概率分组预测值与真实盈利比例、校准误差 |
| 收益排序能力 | 预测收益分组的实际净收益、盈亏比和下行尾部 |
| 覆盖与稳定性 | 可预测信号比例、回退率、有效交易日、不同策略/情绪阶段表现 |
| 账户价值 | 采用概率过滤前后的净值、最大回撤、换手、成本、资金利用率 |
| 时间可信度 | 特征与结果可获得时间、模型冻结时间、历史重建标识 |

固定模型与参数版本，保存每次试验而非只保留最好的一次。历史重建报告与前瞻模拟报告分别标识。

上线门槛采用训练期制定、校准期冻结、测试期确认的标准。没有预先定义的普适胜率或盈亏比数值。未达到覆盖与可靠度要求时仅作为研究参考，不参与交易门禁。

验收：能复现每个窗口预测；测试期没有参与参数选择；显示简单基准；冻结后的前瞻预测持续记录；严重漂移时降级为分组统计或样本不足。

## 9. Phase 5：工作台、模拟交易与微信展示

修改：`web/app.py`、`frontend/src/main.tsx`、`frontend/src/types.ts`、必要样式、`web/templates/strategy_evaluation.html`、`core/notifications/notifier.py`。

工作台证据抽屉增加“相似历史案例”视图：概率、定义、样本区间、预期净收益、盈亏比、收益分布、失败风险和案例表。匹配字段可展开，不用默认占满工作台。

案例走势图对齐各自成交时点，展示标准化收益。每个案例显示匹配依据、事件日期、实际退出原因和成本，支持成功/失败/全部筛选。

模拟交易的买入记录绑定当时forecast_id。交易结束后并排展示当时估计与实际收益，避免用今天重算的概率覆盖当时判断。

API建议：

- `GET /api/signals/{signal_id}/analog-analysis`：读取已冻结评估与当前可用状态。
- `GET /api/signals/{signal_id}/similar-cases`：分页读取匹配明细。
- `GET /api/operations/experiments/{experiment_id}/analog-validation`：读取校准和账户对照。

接口沿用现有鉴权与权限；读取不触发全历史计算。盘中计算由后台确认事件触发，超时或评估未就绪时原有通知照常发送，概率部分标记未就绪。评估完成不能产生重复“买入”提醒。

微信在已有身份与实时确认内容后附上简短评估：盈利概率及定义、预期净收益、盈亏比、样本数/交易日数、可靠度与主要下行风险。仅对可靠度达到展示标准的结果给出具体估计。

验收：工作台与微信引用同一forecast_id；旧预测不会被覆盖；缺失信息不伪造数值；微信仍保持去重与同主题限额；打开页面不重新抓历史行情。

## 10. Phase 6：账户比较与换股实验

实施记录（2026-10-08）：Phase 5 的后台冻结评估、只读分页接口、工作台/微信/成交关联已接通。Phase 6 已增加当前持仓状态归档、同区间比较服务和独立三账户事件回放工具，策略评估可读取报告及净值。真实账户对照尚需完整事件证据与成熟持仓样本，未发布生产过滤/换股开关。详见《相似评估展示与账户对照使用说明.md》。

新增：`core/portfolio/signal_comparison.py`。

扩展：`core/portfolio/paper_trading_service.py`、`core/portfolio/position_monitor.py`、实验与完整账户净值评估。

先做展示和旁路实验，比较四种行动：保持持仓、用现金买入、卖出弱持仓换股、暂不行动。

比较需要考虑：新票预期净收益及其不确定性、持仓从当前时点起的剩余预期收益、同题材/同市场暴露、卖出可行性、现金、交易成本及整体下行风险。

已有持仓不能直接复用买入时预测。其比较基准是当前时点重新冻结的状态，包括持有天数、浮盈亏、当前结构、市场与板块变化；匹配同样处于持仓状态的历史案例。

只有新票模型可靠度、风险预算和扣除换股成本后的优势均满足预先冻结条件，才在独立实验账户中触发换股。保持最多3只、T+1及现有执行约束。

增加完整账户对照：原规则、只使用相似评估过滤新买入、再加入换股。手工成交与实时成交保留在原账户；研究实验使用独立账户。

验收：同题材重复暴露可识别；当日不可卖的持仓不能换出；新票与持仓比较使用同一未来区间；只有账户收益/回撤及成本对照支持时才讨论生产接入。

## 11. 存储、性能与自动任务

新增表建议如下，使用已有数据库，不新增服务：

| 表 | 作用 | 存储位置 |
|---|---|---|
| signal_cases | 不可变案例身份、时间、版本与紧凑特征 | 因子DuckDB；单写任务维护 |
| signal_case_outcomes | 各结果及成熟时间、质量状态 | 同一DuckDB；按行情日增量计算 |
| signal_case_forecasts | 每次信号冻结的评估、版本和样本摘要 | 现有交易SQLite |
| signal_case_matches | 预测匹配到的case_id、距离及权重 | 现有交易SQLite；只保存有限近邻 |

盘后单写任务：补案例 → 补成熟结果 → 发布紧凑只读匹配索引。Web与盘中服务读取索引和冻结预测，避免与DuckDB写入产生争抢。

按策略、日期、成熟状态与版本过滤后再匹配；初版使用分组统计和向量距离，不引入向量数据库或大模型。保留有限近期索引，较老案例留在历史库供离线验证。

历史初始化按日期分段且可接力。只预取案例所需个股及必要板块证据，不全市场重复获取分钟数据。不假定eltdx能覆盖所有旧日期；无法补齐的范围先发布数据覆盖报告。

自动任务接入已有每日20:00流水线：取数与因子完成后补案例和结果；模型验证/发布作为独立低频任务。失败记录日期和原因，重试采用幂等键，不重复写成交或通知。

性能验收建议：在目标服务器与固定样本规模上测量索引加载耗时、单信号评估P95延迟、API缓存响应与内存峰值。先记录基线，再制定上线预算；通知主链路不等待重型回放。

## 12. 交付顺序与最终验收

| 交付批次 | 范围 | 可见结果 |
|---|---|---|
| 第一批 | Phase 0—2 | 修正历史统计、案例覆盖报告、可追溯的成熟结果 |
| 第二批 | Phase 3—4 | 相似案例评估、滚动样本外与概率校准报告 |
| 第三批 | Phase 5 | 工作台、模拟成交和微信看到同一份冻结评估 |
| 第四批 | Phase 6 | 独立账户的过滤/换股对照，再决定生产开关 |

最重要的回归用例：未来信息隔离、结果成熟边界、重复回放去重、部分退出净收益、无法成交、缺数据、同日同主题相关样本、版本变化、手工成交保留、通知不重复、冻结预测不覆盖、持仓T+1与账户对账。

完成标准不是“页面出现一个胜率百分比”，而是任意预测都能回答：用了哪些当时已知案例、为何相似、结果定义是什么、概率是否经过独立验证，以及加入它后完整账户的收益和风险有没有改善。
