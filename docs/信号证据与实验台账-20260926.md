# 信号时点证据、健康门禁与实验台账

## 一条信号的可追溯链

系统把盘中候选识别、模拟委托、模拟成交、持仓变化和通知写入
`HOLDING_DB_PATH` 指向的 SQLite 数据库。`signal_evidence` 保存最近一次时点证据，
`trading_events` 追加不可重复的事件，二者由稳定的 `signal_id` 关联。
同一事件重复处理时按 `event_id` 幂等插入，不会生成重复流水。
手动成交也会写入成交及持仓变化事件，但不一定关联自动信号。

证据包含候选日、行情日、源数据取数时间、行情源时间、本机报价接收时间、
确认分钟收盘时间、板块观测时间和成分股覆盖率、策略配置版本、触发和否决原因，
有模拟成交后补记成交时间。缺失字段保留为空，不用未来价格补写过去的判断。
这些时间各有含义：源端行情时间不是本机收到时间，确认分钟收盘也不是实际成交时间。

管理接口：

- `GET /api/operations/signals/{signal_id}`：证据和统一事件流水。
- `GET /api/operations/health/{trade_date}`：盘后分区、任务、决策池及采集器状态。
- `GET /api/operations/experiments`、`GET /api/operations/experiments/{id}`：实验记录。

## 双健康门禁

盘后门禁检查取数质量及 Silver 分区、五项因子任务成功清单、因子分区、
决策池和页面快照的交易日。盘中使用前还检查它们是否在行情日 09:25 前生成。
盘中门禁检查 Redis（服务器角色）、采集器心跳和租约、批量行情日期、
单股报价接收年龄、板块观测年龄、板块指数及成分股数据完整度。
成分股覆盖率按实际观测数除以最多 80 只应请求成分股，最低 60%。
任一门禁不通过，确认信号降为观察，不发买入通知，也不自动模拟买入。
故障恢复后应重新生成实时载荷；不能把旧确认当成仍可成交。

部署时需让 `WEB_DATA_DIR` 和 `HOLDING_DB_PATH` 可写，并运行完整盘后流水线，
以生成 `fetch_status/fetch_YYYYMMDD.json`、`factor_status/factors_YYYYMMDD.json`、
决策池和快照。此前只有旧因子分区而没有逐项任务记录的日期会被门禁拦截；
需要按原始数据重跑对应日期的因子与选股，不应手写成功标记。
盘中确认依赖活跃采集器；服务器应配置共享 Redis 及
`MARKET_DATA_NODE_ROLE=server`。`/api/operations/health/{trade_date}` 的
盘后状态是该日现状，实际次日信号还会额外校验开盘前时点。

## 策略实验

先执行 `python scripts/strategy_experiment_ledger.py freeze --label 名称`，
记录五个生产策略的配置与因子、筛选、盘中入场、模拟成交代码哈希。
随后执行
`python scripts/strategy_experiment_ledger.py evaluate 实验ID --start YYYYMMDD --end YYYYMMDD --train-days 60 --validation-days 20`。
台账按时间滚动窗口与市场阶段报告候选数、确认率、不可成交信号、
模拟成交率、已实现收益和已实现交易回撤；每个验证日的决策池、
取数状态及快照内容哈希单独保存，避免把不同数据版本混在一起。

冻结前的日期、配置或代码已变更、或者缺少同日原始工件的窗口，
均标为 `historical_descriptive`，不能称为样本外。
只有冻结在验证窗口之前且版本及时点校验通过的窗口才标为
`prospective_oos`。训练窗口用于定义滚动时间切分，本功能不自动训练或调参。
收益只汇总已平仓的模拟交易，不是逐日盯市净值，缺少信号或成交历史时
相应指标为空；不能据此推断策略真实可执行收益。

## 运行边界

SQLite 事件与模拟成交在同一持仓事务内写入；微信属于外部系统，
通知事件只能在发送结果返回后追加记录，无法与微信实现跨系统原子提交。
重试使用稳定事件键降低重复记录风险，但网络超时后的实际送达仍需结合
Server 酱回执核对，不能宣称绝对不重发。
